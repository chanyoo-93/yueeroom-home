# Claude Code + Codex CLI 기반 GitHub Issue 작업 프롬프트 운영 문서

이 문서는 GitHub repository issue 단위로 Claude Code와 Codex CLI를 상보적으로 사용하기 위한 표준 작업 흐름, 입력 프롬프트, 출력 형식을 정의한다. Issue #147 사례를 일반화하여 다른 이슈에도 그대로 재사용할 수 있도록 작성했다.

---

## 1. 전체 작업 흐름

1. Claude Code에게 GitHub issue 구현 계획 작성을 지시한다. 이 단계에서는 코드를 수정하지 않는다.
2. Claude가 만든 계획 문서를 Codex가 읽고 작업 준비 결과를 출력하게 한다. 이 단계에서도 코드는 수정하지 않는다.
3. Codex의 작업 준비 결과를 바탕으로 구현 착수를 지시한다. 수정 범위, 금지 사항, 테스트 명령을 명확히 지정한다.
4. Claude Code에게 현재 브랜치 변경 사항을 리뷰하게 한다. 이 단계에서는 파일을 수정하지 않고 심각도별 리뷰만 출력한다.
5. Claude 리뷰를 Codex용 수정 프롬프트로 정리해 전달한다. 보통 High/Medium만 우선 수정하고 Low는 선택 사항으로 남긴다.

---

## 2. 역할 분담 원칙

| 단계 | Claude Code                                           | Codex CLI                                            |
| ---- | ----------------------------------------------------- | ---------------------------------------------------- |
| 계획 | 이슈 분석, 관련 파일 탐색, 구현 순서·테스트 전략 제안 | 계획 문서 읽기, 작업 범위 재정리                     |
| 구현 | 직접 구현보다는 설계 기준 제공                        | 제한된 범위에서 실제 코드 수정, 테스트 실행          |
| 리뷰 | 현재 브랜치 diff를 구조·아키텍처·테스트 관점에서 리뷰 | 리뷰 항목 중 지정된 심각도만 최소 수정               |
| 통제 | 변경하지 말고 의견만 작성하도록 제한                  | 수정 대상·금지 대상·테스트 명령을 명시하여 범위 통제 |

---

## 3. 공통 파일/브랜치 운영 규칙

- 작업은 반드시 GitHub issue 번호 기준으로 진행한다. 예: issue #147.
- 계획 문서는 `docs/plans/issue-<번호>-plan.md` 형식을 권장한다.
- 계획 문서는 작업 참고용이다. 커밋 포함 여부를 매번 명확히 지시한다.
- 작업 브랜치는 `fix/issue-<번호>-요약`, `feat/issue-<번호>-요약` 등으로 만든다.
- DB schema, migration, seed, 인증 전략, 공통 인프라 등은 명시적으로 허용하지 않는 한 수정 금지 대상으로 둔다.
- 에이전트에게 “코드 수정 금지”, “리뷰만”, “High/Medium만 수정” 같은 상태를 항상 명시한다.

## 4. 1단계 — Claude Code 구현 계획 지시

### 4.1 입력 프롬프트 템플릿

```text
목표:
- 현재 이슈는 GitHub 저장소의 issue #{{ISSUE_NUMBER}} 구현이다.
- 관련 모듈, 파일, 데이터 흐름, 테스트 위치를 탐색한다.
- 바로 코드를 수정하지 않고, 작업 계획만 제안한다.

참고:
- GitHub issue #{{ISSUE_NUMBER}}
- 현재 repository 구조

출력 형식:
1. 관련 파일 목록
2. 현재 구조 요약
3. 변경해야 할 지점
4. 잠재적 위험
5. 구현 순서
6. 테스트 전략

주의:
- 코드는 수정하지 마.
- 파일을 생성하거나 변경하지 마.
- 추측이 필요한 부분은 “확인 필요”로 분리해.
```

### 4.2 Claude 출력 형식

```md
# 작업 계획 — 이슈 #{{ISSUE_NUMBER}}

## 1. 관련 파일 목록

| 파일 | 역할 |
| ---- | ---- |
| ...  | ...  |

## 2. 현재 구조 요약

- ...

## 3. 변경해야 할 지점

- ...

## 4. 잠재적 위험

- ...

## 5. 구현 순서

1. ...
2. ...

## 6. 테스트 전략

- 수정/추가할 테스트
- 실행할 테스트 명령
```

운영 팁: Claude의 출력은 `docs/plans/issue-<번호>-plan.md`로 저장한다. 이후 Codex에게는 이 파일을 “작업 명세서”로 읽게 한다.

## 5. 2단계 — Codex 작업 준비 지시

### 5.1 입력 프롬프트 템플릿

```text
docs/plans/issue-{{ISSUE_NUMBER}}-plan.md 파일을 읽고 GitHub repository issue #{{ISSUE_NUMBER}} 작업을 준비해.

아직 코드는 수정하지 마.

출력:
1. 네가 이해한 작업 목표
2. 수정 대상 파일
3. 구현 순서
4. 테스트 추가/수정 계획
5. 위험 요소
6. 작업 시작 전에 확인이 필요한 점

주의:
- issue-{{ISSUE_NUMBER}}-plan.md의 범위를 벗어난 제안은 하지 마.
- 계획서에서 “변경 불필요” 또는 “수정 금지”로 언급된 파일/함수는 변경하지 않는 것으로 간주해.
- 현재 git status를 확인하고, 계획 문서가 untracked인지 여부도 보고해.
- 이 단계에서는 파일을 수정하지 마.
```

### 5.2 Codex 출력 형식

```text
1. 네가 이해한 작업 목표
- ...

2. 수정 대상 파일
백엔드:
- ...
프론트엔드:
- ...
테스트:
- ...

3. 구현 순서
1. ...
2. ...

4. 테스트 추가/수정 계획
- ...

5. 위험 요소
- ...

6. 작업 시작 전에 확인이 필요한 점
- ...
```

검토 기준: Codex의 준비 출력에서 수정 대상 파일이 과도하게 넓어졌는지, 금지 파일이 포함됐는지, 응답 계약 변경이 명확히 언급됐는지 확인한 뒤 구현 단계로 넘어간다.

## 6. 3단계 — Codex 구현 착수 지시

### 6.1 입력 프롬프트 템플릿

```text
정리한 Issue #{{ISSUE_NUMBER}} 이해 내용을 기준으로 구현을 진행해.

목표:
{{ISSUE_GOAL}}

핵심 원칙:
{{CORE_PRINCIPLES}}

참고 문서:
- docs/plans/issue-{{ISSUE_NUMBER}}-plan.md

중요한 제약:
- 작업 시작 전 메인 브랜치의 최신화 여부를 확인하고, 작업 브랜치로 체크아웃한다.
- 브랜치 네이밍은 fix/issue-{{ISSUE_NUMBER}}-{{SHORT_NAME}} 또는 feat/issue-{{ISSUE_NUMBER}}-{{SHORT_NAME}} 형식을 사용한다.
- docs/plans/issue-{{ISSUE_NUMBER}}-plan.md는 참고만 하고, 코드 변경 대상에 포함하지 마.
- 계획서 범위를 벗어난 리팩토링이나 기능 추가는 하지 마.
- DB schema, migration, seed 파일은 수정하지 마.
- 새 API endpoint는 명시적으로 요구되지 않는 한 추가하지 마.
- {{DO_NOT_TOUCH_LIST}}

수정 대상 파일:
{{TARGET_FILES}}

구현 요구사항:
{{IMPLEMENTATION_REQUIREMENTS}}

테스트 요구사항:
{{TEST_REQUIREMENTS}}

작업 방식:
1. 먼저 실제 현재 코드 상태와 git diff를 확인한다.
2. 위 범위 안에서만 코드를 수정한다.
3. 변경이 커질 경우 백엔드 → 프론트엔드 → 테스트 순서로 나눠 진행한다.
4. 수정 후 관련 테스트를 실행한다.
5. 실패 테스트가 있으면 원인을 설명하고, Issue #{{ISSUE_NUMBER}} 범위 안에서만 수정한다.

우선 실행 권장 테스트:
{{TEST_COMMANDS}}

출력 형식:
1. 변경한 파일 목록
2. 핵심 변경 내용
3. 응답 계약 변경 요약
4. 실행한 테스트 명령
5. 테스트 결과
6. 실패한 테스트가 있다면 원인과 조치 내용
7. 남은 위험 요소
8. 커밋 전 확인해야 할 사항

주의:
- 한 번에 전체 구조를 갈아엎지 마.
- 계획서에 있는 Issue #{{ISSUE_NUMBER}} 범위만 구현해.
- 보안/인증 이슈라면 기존보다 취약한 흐름을 다시 만들지 마.
```

### 6.2 구현 지시 작성 체크리스트

- 목표는 한 문단으로 명확히 적는다.
- 핵심 원칙은 “해야 할 것”과 “하면 안 되는 것”을 모두 포함한다.
- 수정 대상 파일과 수정 금지 파일을 분리한다.
- 테스트 명령을 구체적으로 적는다.
- 계획 문서가 untracked라면 커밋 대상에서 제외하라고 명시한다.
- 출력 형식을 지정해 작업 결과를 다시 다음 단계 입력으로 재사용할 수 있게 한다.

## 7. 4단계 — Claude Code 브랜치 리뷰 지시

### 7.1 입력 프롬프트 템플릿

```text
현재 브랜치의 변경 내역을 검토해줘.

참고:
- 현재 브랜치는 issue #{{ISSUE_NUMBER}}의 구현이다.
- docs/plans/issue-{{ISSUE_NUMBER}}-plan.md가 있다면 참고하되, 커밋 대상 여부도 확인해줘.

관점:
- 책임 분리가 적절한가?
- 기존 아키텍처와 어긋나는 부분이 있는가?
- 중복 코드가 생겼는가?
- 테스트가 충분한가?
- 향후 유지보수 위험이 있는가?
- 보안/인증/응답 계약 변경이 있다면 회귀 위험이 있는가?

주의:
- 바로 수정하지 말고 리뷰 의견만 작성해줘.
- 파일을 변경하지 마.
- 반드시 심각도별로 분류해줘.

출력 형식:
[Critical]
- ...

[High]
- ...

[Medium]
- ...

[Low]
- ...

[종합]
- PR 가능 여부
- 릴리즈 전 반드시 처리할 항목
- 선택적으로 처리할 항목
```

### 7.2 Claude 리뷰 출력 형식

```text
코드 리뷰 — Issue #{{ISSUE_NUMBER}} ({{ISSUE_TITLE}})

[High] N건
---
H1. {{파일명}} — {{문제 제목}}
- 문제 설명
- 영향 범위
- 권고 수정 방향

[Medium] N건
---
M1. {{파일명}} — {{문제 제목}}
- 문제 설명
- 권고 수정 방향

[Low] N건
---
L1. {{파일명}} — {{문제 제목}}
- 문제 설명
- 선택 수정 여부

종합
- 핵심 목표 달성 여부
- 릴리즈 전 처리 권고 항목
- PR 가능 여부
```

## 8. 5단계 — Codex 리뷰 반영 지시

### 8.1 입력 프롬프트 템플릿

```text
Claude Code가 Issue #{{ISSUE_NUMBER}} 구현 결과를 리뷰했고, {{SEVERITY_SUMMARY}}를 지적했다.

목표:
- Issue #{{ISSUE_NUMBER}}의 핵심 구현 범위 안에서 Claude review의 {{FIX_SEVERITIES}} 항목만 수정한다.
- {{DEFERRED_SEVERITIES}} 항목은 수정하지 말고, 마지막에 “선택 수정 가능”으로만 보고한다.
- 기능 범위를 넓히거나 새로운 구조를 추가하지 않는다.

참고 문서:
- docs/plans/issue-{{ISSUE_NUMBER}}-plan.md
- 현재 git diff
- Claude review 요약

Claude review 핵심 내용:
{{CLAUDE_REVIEW_SUMMARY}}

수정 대상:
{{FIX_TARGET_FILES}}

수정하지 말 것:
{{DO_NOT_TOUCH_LIST}}

구현 요구사항:
{{FIX_REQUIREMENTS}}

테스트 요구사항:
{{FIX_TEST_REQUIREMENTS}}

Low/선택 항목 처리:
{{DEFERRED_ITEMS_POLICY}}

작업 순서:
1. 현재 git diff와 관련 파일을 확인한다.
2. 수정 계획을 5줄 이내로 요약한다.
3. 높은 심각도 항목부터 수정한다.
4. 관련 테스트를 실행한다.
5. 실패가 있으면 Issue #{{ISSUE_NUMBER}} 범위 안에서만 수정한다.

우선 실행할 테스트:
{{FIX_TEST_COMMANDS}}

출력 형식:
1. 변경한 파일 목록
2. 해결한 Claude review 항목
{{REVIEW_ITEM_OUTPUT_LIST}}
3. 수정하지 않은 선택 항목과 이유
4. 실행한 테스트 명령
5. 테스트 결과
6. 남은 위험 요소
7. 커밋 전 확인 사항

주의:
- Claude review의 지정 심각도만 해결한다.
- 새로운 리팩토링을 하지 않는다.
- 기존 보안/인증 개선 방향을 되돌리지 않는다.
- 계획 문서를 임의로 수정하거나 커밋 대상으로 추가하지 않는다.
```

### 8.2 심각도별 수정 정책

| 심각도   | 기본 정책           | Codex 지시 방식                                                  |
| -------- | ------------------- | ---------------------------------------------------------------- |
| Critical | 반드시 수정         | 즉시 수정. 테스트 실패 시 원인 분석 후 범위 안에서 재수정.       |
| High     | 릴리즈 전 수정 권장 | 우선 수정 대상. 기능/보안/아키텍처 영향이 크므로 명확히 반영.    |
| Medium   | 가능하면 함께 수정  | High와 같은 파일 또는 테스트라면 함께 수정.                      |
| Low      | 선택 수정           | 기능 결함이 아니면 보고만 하고 보류. 별도 지시가 있을 때만 수정. |

## 9. Issue #147 적용 예시 요약

- 이슈 목표: access_token을 프론트 JS가 읽는 흐름에서 백엔드 httpOnly 쿠키 기반 흐름으로 전환.
- Claude 계획 산출물: `docs/plans/issue-147-plan.md`.
- Codex 준비 단계: 작업 목표, 수정 대상 파일, 구현 순서, 테스트 수정 계획, 위험 요소를 출력.
- Codex 구현 단계: auth, frontend client, login/register/pending/AdminGuard/UserMenu/middleware와 테스트를 수정.
- Claude 리뷰 단계: High 2건, Medium 2건, Low 2건을 심각도별로 출력.
- Codex 리뷰 반영 단계: High/Medium만 수정하고 Low는 선택 항목으로 보류.

## 10. 최종 PR 전 체크리스트

- git diff에 계획 문서, 임시 로그, 불필요한 파일이 포함되지 않았는가?
- Codex가 수정 금지 파일을 건드리지 않았는가?
- Claude 리뷰의 Critical/High/Medium이 모두 처리되었는가?
- Low 항목을 보류했다면 그 이유가 PR 설명에 남아 있는가?
- 관련 테스트 명령을 실제로 실행했고 결과를 기록했는가?
- 응답 계약 변경이 있다면 프론트/백엔드/테스트가 동시에 맞춰졌는가?
- 보안 이슈라면 기존 취약 흐름이 다시 생기지 않았는가?
- 커밋 메시지가 issue 번호와 변경 범위를 명확히 표현하는가?

## 권장 운영 방식

Claude는 계획과 리뷰에 강하게 사용하고, Codex는 준비 출력과 구현·수정에 사용한다. 각 단계의 출력이 다음 단계의 입력이 되도록 출력 형식을 고정하면 반복 작업의 품질이 안정된다.
